# Architecture

## Purpose

Ready-to-use Japanese interregional freight flow data, starting with the interprefectural tables (都道府県間流動表) of 全国貨物純流動調査 (the logistics census, 物流センサス):

| Table | Contents | Getter |
|---|---|---|
| IV-1-1 | Weight by commodity class (品類) | `logistics_census_flow_get(year, by = "commodity_class")` |
| IV-1-2 | Number of shipments by commodity class | `logistics_census_flow_get(year, by = "commodity_class")` |
| IV-2 | Weight by commodity (品目) | `logistics_census_flow_get(year, by = "commodity")` |
| V-1-1 | Weight by representative transport mode (代表輸送機関) | `logistics_census_flow_get(year, by = "mode")` |
| V-1-2 | Weight by truck mode and the use of expressways | `logistics_census_flow_get(year, by = c("mode", "expressway"))` |
| V-2 | Weight by mode and commodity class | `logistics_census_flow_get(year, by = c("mode", "commodity_class"))` |
| VI-1 | Travel time by mode | `logistics_census_time_get(year)` |
| VI-2 | Freight rate by mode and commodity class | `logistics_census_freight_rate_get(year)` |

The package name is kept generic, like freightdataus, so that it can hold interregional data from other sources (see the roadmap). The title of the package states that the data are interregional.

Out of scope: passenger flows, modeling, transformations for a particular analysis, and redistributing data.

## Layout

- `inst/tarchives/logistics-census-pref-<year>/_targets.R`: one tarchives pipeline per survey year, with every table of that year. The other tables are parsed with the zone table of the same year.
- `inst/tarchives/R/`: helpers shared by the pipelines. Source files are downloaded into the `user` directory of the targets store, never into the installed package.
- `R/`: for each kind of value, a getter (`<object>-get.R`) that wraps `tarchives::tar_get_archive_raw()`, and a target factory (`<object>-target.R`) that wraps `tarchives::tar_target_archive_raw()`.
- `tests/testthat/fixtures/`: synthetic cells that mimic both workbook layouts for a three-zone system, generated by `make-fixtures.R`. The pipeline helpers are tested on these, not on the published workbooks.

## Naming

- `logistics_census_<object>_get()` returns a table, for example `logistics_census_flow_get()`. There is one getter per kind of value (flow, travel time, freight rate, zone), not per published table.
- `by` chooses the breakdown of the flow tables, and so the published table. It is required, and its elements can be in any order. The target of a breakdown is named `flow_<by>`, in the order of `logistics_census_flow_by` (for example `flow_mode_commodity_class`).
- `logistics_census_<object>_target()` and `logistics_census_<object>_target_raw()` declare a target that reads the same table, for use in other pipelines. The first captures `name` with non-standard evaluation; the second takes a string.

## No hard-coded classifications

Functions take the zone system and other classifications as data, so that they keep working if the classification changes.

- The available years are those of the bundled `logistics-census-pref-<year>` pipelines.
- Anything that differs by year (source URLs, sheets, the keys of labels, the notation of angles) is passed explicitly in that year's `_targets.R`. Functions have no default arguments for it, and no year is used as a default.
- The prefecture codes and names come from the zone table. The parsers find the header row, the origins, and the destinations by matching zone names, and check that every zone was found.
- The labels of each table (commodity, commodity class, mode, expressway) are read from the workbook, and the parser checks that every table has every label.
- Notation is normalized by rules (for example, a trailing `計` other than `合計` becomes `（小計）`), not by lookup tables of labels.
- No values are aggregated: totals are dropped, never computed.

## Output

Every getter returns a long tibble.

Column naming, shared by freightdatajp and freightdataus:

- `_code` is a code from an official classification, `_id` is an arbitrary record identifier, and `_name` is a label.
- Both packages use the same column names. A column is omitted when the source has nothing to put in it.
- Words are spelled out (`longitude`, not `lon`). The one exception is counts, which are named `n_<things>` (for example `n_shipments`), following `n` from `dplyr::count()` and `n()`.
- Physical quantities are `units` columns, so names carry no unit suffix. Weight is in `t` (metric tonnes), distance in `km`, and time in `h`. Convert with `units::set_units()`, never by hand.
- Money stays numeric with the currency in the name (`value_usd`), because udunits has no currencies, and registering one with `units::install_unit()` would change the unit system of the user's whole session.

| Table | Keys | Values |
|---|---|---|
| Zone | `year`, `zone_code` | `zone_name`, `longitude`, `latitude` |
| Flow, `by = "commodity"` | `year`, `commodity_name`, `origin_code`, `destination_code` | `weight` |
| Flow, `by = "commodity_class"` | `year`, `commodity_class_name`, `origin_code`, `destination_code` | `weight`, `n_shipments` |
| Flow, `by = "mode"` | `year`, `mode_name`, `origin_code`, `destination_code` | `weight` |
| Flow, `by = c("mode", "expressway")` | `year`, `mode_name`, `expressway`, `origin_code`, `destination_code` | `weight` |
| Flow, `by = c("mode", "commodity_class")` | `year`, `mode_name`, `commodity_class_name`, `origin_code`, `destination_code` | `weight` |
| Time | `year`, `mode_name`, `origin_code`, `destination_code` | `travel_time` |
| Freight rate | `year`, `mode_name`, `commodity_class_name`, `origin_code`, `destination_code` | `freight_rate_jpy_per_tonne_km` |

- `zone_code`, `origin_code`, and `destination_code` are two-digit prefecture codes (`"01"` to `"47"`, JIS X 0401), stored as character. Other tables carry only the codes; names and points are in the zone table, to be joined when needed. Do not combine a code and a name into one identifier (such as `01_hokkaido`) in a data column.
- There is no pair table. The published tables have nothing at the level of a zone pair, and every pair of zones is `tidyr::expand_grid()` of the zone codes. Add one only for published pair-level data, such as distances.
- If another zone system is added (for example the 207 zones of 生活圏), give the getters an argument for it, as freightdataus does with `geography`, so that codes of different systems are never mixed.
- The published tables have no commodity, commodity class, or mode codes, so there are no `_code` columns for them.
- `expressway` is logical: `TRUE` for shipments that used an expressway.
- The weight (IV-1-1) and the number of shipments (IV-1-2) by commodity class have the same breakdown, so they are joined into one table, and the join must match every row.
- Intra-prefecture rows (`origin_code == destination_code`) are kept.
- Total rows and total columns (`合計`) over prefectures are dropped. Commodity, commodity class, and mode labels are kept as published, so their subtotals (for example `鉄道（小計）`) and totals (`合計`) remain rows.
- A published zero is `0`. A suppressed or blank cell is `NA`. The flow tables have no blank cells; the time and freight rate tables leave a cell blank where there were no shipments.
- Values are as published: tonnes and numbers of shipments over the three-day survey period, hours per shipment, and yen per tonne-km.

### Representative points

`longitude` and `latitude` are the population centroids published by the Statistics Bureau, in decimal degrees in the Japanese Geodetic Datum 2000 (世界測地系). They are plain numeric columns, not `units`, so that they can be passed to `sf::st_as_sf()` directly.

Population centroids move between censuses, so the zone table is provided by survey year, using the census of that year or the latest one before it:

| Survey year | Census | Source | Notation |
|---|---|---|---|
| 2005 | 2005 | 2005 census, final report, table 14 (e-Stat `statInfId=000007375683`) | DMS packed as `DDDMMSS.ss` |
| 2010 | 2010 | 2010 census, final report, table 14 (e-Stat `statInfId=000025518687`) | DMS packed as `DDDMMSS.ss` |
| 2015 | 2015 | Statistical Topics No. 102, one sheet per prefecture | DMS packed as `DDDMMSS.ss` |
| 2021 | 2020 | Statistical Topics No. 135, sheet `全国` | Decimal degrees |

- Coordinates are parsed with `parzer::parse_lon()` and `parzer::parse_lat()`, which also check their ranges. parzer can't read packed DMS, so it is first written out as `137°00'27.43"` with `stringr`.
- The 2005 and 2010 tables also list the previous census, recomputed on current boundaries. Only the first longitude and latitude columns, those of the census year, are read.
- The datum is stated as 世界測地系 for 2015 and 2020. For 2005 and 2010, the 2005 values in the 2005 and 2010 tables are identical, and the movements of the national centroid computed from the tables (1.6 km to the south-southeast from 2010 to 2015, 2.2 km to the southeast from 2015 to 2020) match those the Statistics Bureau publishes, so the series is in one datum.
- Between consecutive censuses, prefectural centroids move by 0.3 to 0.4 km (median) and at most 1.4 km.

Three candidates were compared by how well the great-circle distance between points explains the published travel times by truck of the same survey year (R² of `log(travel_time) ~ log(distance) + mode` over interprefectural pairs within Hokkaido, Honshu, Shikoku, or Kyushu, truck modes only):

| Candidate | Source | 2005 | 2010 | 2015 | 2021 |
|---|---|---|---|---|---|
| Population centroid (census of the survey year) | Statistics Bureau | **0.741** | **0.822** | **0.748** | **0.680** |
| Geometric centroid | 国土数値情報 N03 (2025) | 0.735 | 0.813 | 0.741 | 0.672 |
| Prefectural government office | 国土数値情報 P28 (2022) | 0.725 | 0.810 | 0.738 | 0.668 |

The population centroid was chosen because:

- It fits best in every survey year.
- It is published for every census, so it follows the survey year. N03 and P28 are published for other reference dates.
- It is a small workbook read with `readxl`, while N03 is a 632 MB download that needs `sf`.
- P28 may be used only for non-commercial purposes, and that restriction would carry over to the output.
- The geometric centroid is pulled off the main land masses by remote islands (Tokyo's lies in the sea because of the Ogasawara Islands, and Hokkaido's is shifted east).

The trade-off is that the population centroids of Nagasaki (42), Oita (44), and Okinawa (47) lie in the sea, which matters if the points are snapped to a network. If that is needed, add the prefectural government offices as a separate pair of columns rather than replacing these.

## Consistency across years

- Every year returns the same columns, with the same types and units. The two workbook layouts (2005 to 2015, and 2021) must produce identical output.
- Known variants in notation are normalized so that the same label is used in every year. The 2021 spelling is used:
  - `染料･顔料･塗料` (half-width `･`, 2005 to 2015) becomes `染料・顔料・塗料`.
  - Mode subtotals `<mode>計` (2005 to 2015, for example `鉄道計`) become `<mode>（小計）`. `合計` is the total over all modes and is left as is.
  - The use of expressways, `利用あり`/`利用なし` (2005 to 2015) and `利用する`/`利用しない` (2021), becomes `TRUE`/`FALSE`.
  - Whitespace inside labels is removed.
- The 85 commodities, 10 commodity classes (including `合計`), and 17 modes are the same in every year once normalized.
- If the classification itself changes between survey rounds (commodities split or merged), keep the published labels and document the change; do not harmonize silently.
- A test checks that both layouts give the same column names and types.

The workbooks come in two layouts:

- **2005 to 2015**: one table per block, on one sheet or one sheet per mode (V-1-2, V-2, VI-2).
  - Above each block is a row of label keys and values, for example `代表輸送機関 | 鉄道コンテナ | | | 品類名 | 農水産品`. The keys are published spaced (`品　目　名`). Sheet names are abbreviated in half-width kana (`鉄道ｺﾝﾃﾅ`), so labels are never read from them.
  - The header row is the row whose second cell is a zone name.
  - Prefecture names are abbreviated by dropping the trailing `都`, `府`, or `県` (for example `東京`), and cells contain stray whitespace.
- **2021**: one table per sheet. The labels are in the title, for example `（１）代表輸送機関：鉄道コンテナ－（１）品類：農水産品［３日間調査］`. The header row is again the row whose second cell is a zone name.

The keys of the labels differ by year (`品目名`, `品類名`, and `高速道路利用の有無` in 2005 to 2015; `品目`, `品類`, and `高速道路` in 2021), so each pipeline passes them, as `labels = c(mode = "代表輸送機関", commodity_class = "品類名")`.

Workbooks are read as cells in the long format of tidyxl (`row`, `col`, `chr`) and parsed with unpivotr. tidyxl itself can't read `.xls`, which 2005 to 2015 use, so every workbook is read with readxl and converted with `unpivotr::as_cells()`, giving one code path for all years.

One parser handles both layouts, following the unpivotr way for several tables on one sheet (split at the corners, then read each table on its own):

- Label keys and values are read both as a key cell followed by its value in the same row, and as `<key>：<value>` within a cell.
- The rows with labels are the top-left corners of the tables, and `unpivotr::partition()` splits the sheet there. The number of tables must equal the number of header rows, so that a table whose labels are missing is an error, not dropped.
- Each table takes its labels from its own cells, each exactly once.
- Below the header row, `unpivotr::behead()` takes the destinations from the header row and the origins from the first column, keeping blank cells as `NA`. Only rows and columns labeled with a zone are kept.

The parsed tables were checked against each other for every year, which catches a label or a block boundary in the wrong place. These hold for every origin and destination, with a largest relative difference of 5e-16:

- The weight by mode and commodity class adds up to the weight by mode (V-2 and V-1-1).
- The commodity classes add up to their total, `合計` (IV-1-1).
- The commodities add up to the total of the commodity classes (IV-2 and IV-1-1).
- The total over modes equals the total over commodity classes (V-1-1 and IV-1-1).

The weight with and without expressways (V-1-2) doesn't add up to the weight by mode (V-1-1): it comes to 47% to 88% of it, depending on the mode and year, and never exceeds it for any pair. Shipments whose use of expressways isn't known are presumably left out of V-1-2. This is documented in `logistics_census_flow_get()`, and the values are returned as published.

## Dependencies

- `Imports`: packages that `R/` uses (`tarchives`, `targets`, `rlang`, `cli`, `purrr`, `stringr`, `tibble`, `units`). `tibble` and `units` are imported so that their print methods are available. Arguments are checked with rlang's `check_*()` functions (exported since rlang 1.3.0, so no standalone file is needed), and errors are raised with `cli::cli_abort()`, in `R/` and in the pipelines alike.
- Tooling: `README.qmd` is rendered to `README.md` with `devtools::build_readme()`, code is formatted with Air (`air.toml`), and GitHub Actions run `R CMD check`, the Air format check, a zizmor audit of the workflows, and the pkgdown site (deployed with GitHub Pages' own deployment). Actions are pinned to commit SHAs, which Dependabot keeps up to date, and each workflow is given only the permissions it needs.
- `Suggests`: packages used only inside the pipelines (`readxl`, `unpivotr`, `parzer`, `curl`, `fs`, `dplyr`, `tidyr`, `vctrs`, `tarchetypes`), and in tests (`readr`, `testthat`).
- Code uses tidyverse and r-lib packages rather than their base equivalents: `stringr` for strings, `fs` for paths, `purrr` for iteration, `purrr::list_rbind()` for binding rows, `vctrs::vec_match()` and `vctrs::vec_in()` for matching, `dplyr` for joins, `tidyr` for reshaping, `unpivotr` for spreadsheet layouts, `parzer` for coordinates, and `readr` for CSV files.

## Storage

The data are small, so targets' default storage (rds) is used and the tables are kept in the store. Per survey year, the largest tables are the freight rates (about 600 KB, 375,530 rows) and the flows by mode and commodity class (about 420 KB); the others are under 300 KB. Most of a store is the downloaded workbooks (about 54 MB for all four years). If a future table is large, store it as Parquet and return it lazily instead.

Building every table of a year takes about 70 seconds (2005 to 2015) to 120 seconds (2021, whose V-2 and VI-2 come in 34 files). Label keys written as `<key>：<value>` are searched for only in cells that contain `：`, because matching every cell of the largest workbooks took minutes.
